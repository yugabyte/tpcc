# The TPC-C Workload (as implemented in this repo)

This document explains what TPC-C is, how this tool models it, and exactly which SQL each
transaction issues. Where this implementation deviates from the
[TPC-C specification (rev 5.11)](http://www.tpc.org/tpc_documents_current_versions/pdf/tpc-c_v5.11.0.pdf),
the deviation is called out. Results from this tool are **not** audited TPC-C results.

## 1. What TPC-C models

TPC-C simulates the order-entry system of a wholesale supplier:

- The company has **W warehouses**. W is the *scale factor* (`--warehouses`).
- Each warehouse supplies **10 districts**.
- Each district serves **3,000 customers**.
- The company sells **100,000 items**, and every warehouse keeps a **stock** record for every item.
- Customers place **orders** made of 5–15 **order lines**. New orders sit in a **NEW_ORDER**
  queue until a **Delivery** transaction processes them.

Everything except `ITEM` scales linearly with W, so a run is described by its warehouse count
(e.g. "a 1,000-warehouse run").

## 2. Terminals: the closed-loop load model

TPC-C is a *closed-loop* benchmark: load comes from a fixed population of emulated users
("terminals"), not from an open arrival rate.

- **10 terminals per warehouse** (`terminals = warehouses * 10`, in `DBWorkload.main`).
- `BenchmarkModule.createTerminals()` assigns each terminal a **home warehouse** and **exactly one
  district** (10 terminals ÷ 10 districts). Each terminal is a `Worker` thread.
- Each terminal loops (`Worker.run()`):
  1. **Fetch work**: take the next transaction type from the shared queue.
  2. **Keying time**: sleep a fixed time (simulates a user typing the input screen).
  3. **Execute** the transaction (with retries, see §6.6).
  4. **Think time**: sleep a random, negative-exponentially distributed time (simulates a user
     reading the output screen).

| Transaction | Keying time (TPC-C 5.2.5.2) | Mean think time (TPC-C 5.2.5.4) |
|-------------|-----------------------------|---------------------------------|
| NewOrder    | 18 s | 12 s |
| Payment     | 3 s  | 12 s |
| OrderStatus | 2 s  | 10 s |
| Delivery    | 2 s  | 5 s  |
| StockLevel  | 2 s  | 5 s  |

Think time is `-ln(U) * mean`, capped at `10 * mean`. Both delays can be switched off with
`<useKeyingTime>false</useKeyingTime>` / `<useThinkTime>false</useThinkTime>`, which turns the
benchmark into an "as fast as possible" stress test. Efficiency (§8) is then meaningless.

Because of these delays, a single terminal spends almost all its time sleeping. That is why the
number of **database connections** (`--num-connections`) is much smaller than the number of
terminals: a terminal borrows a pooled connection only while it executes a transaction.

## 3. Transaction mix

The mix comes from `<transactiontypes>` in the workload XML. The default matches the spec's
minimum percentages:

| Transaction | Weight | Type | Notes |
|-------------|-------:|------|-------|
| NewOrder    | 45 | read-write | The tpmC metric counts these |
| Payment     | 43 | read-write | |
| OrderStatus | 4  | read-only  | |
| Delivery    | 4  | read-write | "batch" transaction |
| StockLevel  | 4  | read-only  | runs in autocommit mode |

`Phase.chooseTransaction()` picks a type at random in proportion to the weights. `ThreadBench`
pushes chosen types into a shared queue at `<rate>` requests per second (queue capped at 10,000;
the oldest entries are dropped when it overflows). With keying and think times on, the terminals,
not `<rate>`, limit throughput.

> **Invariant:** the transactions must be listed in the order
> NewOrder, Payment, OrderStatus, Delivery, StockLevel. Several reporting paths in
> `DBWorkload` hard-code that order and 5 types (see [CODE_REVIEW_GUIDE.md](CODE_REVIEW_GUIDE.md)).

## 4. Schema

Nine tables. Definitions live in `src/com/oltpbenchmark/schema/TPCCTableSchemas.java`; DDL is
generated by `DefaultSchemaManager` (or `GeoPartitionedSchemaManager`). The primary key syntax
depends on `<dbtype>`: YugabyteDB gets explicit `HASH` sharding; PostgreSQL gets plain B-tree keys.

| Table | Rows per warehouse | YugabyteDB primary key | PostgreSQL primary key |
|-------|-------------------:|------------------------|------------------------|
| `WAREHOUSE`  | 1 | `(w_id)` *(hash by default)* | `(w_id)` |
| `DISTRICT`   | 10 | `((d_w_id,d_id) HASH)` | `(d_w_id,d_id)` |
| `CUSTOMER`   | 30,000 | `((c_w_id,c_d_id) HASH, c_id)` | `(c_w_id,c_d_id,c_id)` |
| `HISTORY`    | 30,000 initially, grows | *none* (YugabyteDB adds a hidden row id) | *none* |
| `OORDER`     | 30,000 initially, grows | `((o_w_id,o_d_id) HASH, o_id)` | `(o_w_id,o_d_id,o_id)` |
| `NEW_ORDER`  | 9,000 initially | `((no_w_id,no_d_id) HASH, no_o_id)` | `(no_w_id,no_d_id,no_o_id)` |
| `ORDER_LINE` | ~300,000 initially, grows | `((ol_w_id,ol_d_id) HASH, ol_o_id, ol_number)` | `(ol_w_id,ol_d_id,ol_o_id,ol_number)` |
| `STOCK`      | 100,000 | `(s_w_id HASH, s_i_id ASC)` | `(s_w_id,s_i_id)` |
| `ITEM`       | 100,000 total (not per warehouse) | `(i_id)` *(hash by default)* | `(i_id)` |

The table is called `OORDER` (not `ORDER`) because `ORDER` is a reserved word.

**Secondary indexes** (created right after the tables):

| Index | YugabyteDB | PostgreSQL | Serves |
|-------|-----------|------------|--------|
| `idx_customer_name` | `customer ((c_w_id,c_d_id) HASH, c_last, c_first)` | `customer (c_w_id,c_d_id,c_last,c_first)` | Customer lookup by last name (Payment, OrderStatus) |
| `idx_order` (UNIQUE) | `oorder ((o_w_id,o_d_id) HASH, o_c_id, o_id DESC)` | `oorder (o_w_id,o_d_id,o_c_id,o_id DESC)` | "Newest order of a customer" (OrderStatus) |

**Foreign keys** (10 of them) are added *after* loading, as `NOT VALID` constraints, so existing
rows are not re-scanned:

```
DISTRICT(d_w_id)                      -> WAREHOUSE(w_id)
CUSTOMER(c_w_id,c_d_id)               -> DISTRICT(d_w_id,d_id)
STOCK(s_w_id)                         -> WAREHOUSE(w_id)
STOCK(s_i_id)                         -> ITEM(i_id)
OORDER(o_w_id,o_d_id,o_c_id)          -> CUSTOMER(c_w_id,c_d_id,c_id)
NEW_ORDER(no_w_id,no_d_id,no_o_id)    -> OORDER(o_w_id,o_d_id,o_id)
HISTORY(h_c_w_id,h_c_d_id,h_c_id)     -> CUSTOMER(c_w_id,c_d_id,c_id)
HISTORY(h_w_id,h_d_id)                -> DISTRICT(d_w_id,d_id)
ORDER_LINE(ol_w_id,ol_d_id,ol_o_id)   -> OORDER(o_w_id,o_d_id,o_id)
ORDER_LINE(ol_supply_w_id,ol_i_id)    -> STOCK(s_w_id,s_i_id)
```

**Server-side routines** (created by `--create=true` or `--create-sql-procedures=true`):

- `updatestock1` … `updatestock15`: SQL procedures that update *N* `STOCK` rows of one warehouse
  in a single call, written as a chain of CTEs (`WITH update_cte1 AS (UPDATE ...), ... SELECT 1`).
  NewOrder uses them when `<useStoredProcedures>true</useStoredProcedures>`.
- `getstockcounts(warehouse, district, min_o_id, max_o_id, max_quantity)`: a PL/pgSQL function used
  by StockLevel.

### Why the YugabyteDB keys look like this

In YugabyteDB, rows are distributed across tablets by the hash of the `HASH` columns. The keys
are chosen so that:

- All rows a transaction touches for one `(warehouse, district)` share one hash prefix. Range
  scans on the remaining columns (e.g. "lowest `no_o_id`" in Delivery, "last 20 orders" in
  StockLevel) stay within one tablet and are ordered.
- `STOCK` hashes on `s_w_id` only, with `s_i_id ASC`, so NewOrder's
  `WHERE s_w_id = ? AND s_i_id IN (...)` goes to one tablet.
- Load spreads evenly across the cluster as the warehouse count grows.

See [YUGABYTEDB_CHANGES.md](YUGABYTEDB_CHANGES.md) for the history behind these choices.

## 5. Initial data population

`--load=true` runs `Loader.createLoaderThreads()`:

- **One thread loads `ITEM`**, and only if `--start-warehouse-id` is 1. When several clients each
  load a slice of the warehouses, only the first slice loads `ITEM`.
- **One thread per warehouse** loads, in order: `WAREHOUSE`, `STOCK`, `DISTRICT`,
  `CUSTOMER` + `HISTORY`, then `OORDER` + `NEW_ORDER` + `ORDER_LINE`.
- **A final thread** waits for every warehouse thread, then adds the foreign keys (unless FKs are
  disabled, see [CONFIGURATION.md](CONFIGURATION.md)).
- At most `--loaderthreads` threads run at once (default `min(10, warehouses)`).
- Rows are inserted in JDBC batches of `<batchSize>` (default 128) and committed per batch. The
  driver option `reWriteBatchedInserts=true` turns each batch into multi-row `INSERT`s.
- A failed batch is retried up to `<maxLoaderRetries>` times. Each retry uses a fresh
  `PreparedStatement`, because a statement that has already failed cannot always be reused.

What gets generated (per TPC-C clause 4.3.3.1):

| Data | Rule |
|------|------|
| `ITEM` | `i_price` 1.00–100.00; `i_data` 22–49 chars (spec: 26–50, see the note below), 10% contain `"ORIGINAL"` |
| `WAREHOUSE`, `DISTRICT` | `w_ytd = 300000`, `d_ytd = 30000`; tax 0–0.2; `d_next_o_id = 3001` |
| `STOCK` | `s_quantity` 10–100; `s_data` 22–49 chars, 10% contain `"ORIGINAL"`; ten 23-char `s_dist_xx` strings (spec: 24) |
| `CUSTOMER` | 10% bad credit (`"BC"`); `c_last` for `c_id` 1–1000 is the syllable name of `c_id-1`, and NURand(255) for the rest; `c_balance = -10`, `c_credit_lim = 50000` |
| `HISTORY` | one row per customer, `h_amount = 10` |
| `OORDER` | 3,000 per district; `o_c_id` is a random permutation of 1–3000; `o_carrier_id` set only for `o_id < 2101` |
| `NEW_ORDER` | the last 900 orders per district (`o_id` 2101–3000) |
| `ORDER_LINE` | 5–15 per order; delivered lines (`o_id < 2101`) have `ol_amount = 0` and a delivery date; undelivered lines have a random amount and NULL date |

Note: `TPCCUtil.randomStr(n)` returns `n-1` characters, so random alphanumeric strings are one
character shorter than the spec ranges the loader asks for (see §9). The table above gives the
lengths actually produced where that matters.

As a rough sizing guide, expect on the order of 100 MB of raw data per warehouse. Multiply by the
replication factor, and check the size on a small load before sizing a large cluster.

## 6. The five transactions

All procedures live in `src/com/oltpbenchmark/benchmarks/tpcc/procedures/`. Each extends
`api/Procedure` and implements `run(conn, gen, terminalWarehouseID, numWarehouses,
districtLow, districtHigh, worker)`.

`Worker.executeWork()` passes the district range like this:

- NewOrder, Payment, OrderStatus: `1..10` (pick a random district, per spec 2.4.1.2 / 2.5.1.2 / 2.6.1.2).
- Delivery, StockLevel: the terminal's own fixed district for both bounds.

Unless noted, a transaction runs with `autoCommit=false` at the configured isolation level
(default config: `REPEATABLE READ`, which is snapshot isolation in YugabyteDB), and
`Worker.executeWork()` commits at the end.

### 6.1 NewOrder (45%): place an order

**Inputs** (`NewOrder.run`): random district; customer `NURand(1023, 1, 3000)`; 5–15 items, each
`NURand(8191, 1, 100000)` with quantity 1–10. Each item comes from a **remote supplying warehouse**
with 1% probability (from the same geo-partition if geo-partitioning is on). In **1% of orders the
last item id is set to `-12345`** (unused), forcing the required rollback.

**SQL, in order** (`newOrderTransaction`):

1. `SELECT c_discount, c_last, c_credit FROM customer WHERE c_w_id=? AND c_d_id=? AND c_id=?`
2. `SELECT w_tax FROM warehouse WHERE w_id=?`
3. `UPDATE district SET d_next_o_id = d_next_o_id + 1 WHERE d_w_id=? AND d_id=? RETURNING d_next_o_id, d_tax`
   (the new order id is `returned d_next_o_id - 1`). This one row per district is the main
   **contention hotspot** of TPC-C.
4. `INSERT INTO oorder (...) VALUES (...)`
5. `INSERT INTO new_order (...) VALUES (...)`. `OORDER` is written first because of the FK.
6. For **each distinct supplying warehouse**:
   - `SELECT i_id, i_price, i_name, i_data FROM item WHERE i_id IN (?, ?, ...)`
   - `SELECT s_w_id, s_i_id, s_quantity, s_data, s_ytd, s_remote_cnt, s_dist_01..10 FROM stock WHERE s_w_id=? AND s_i_id IN (?, ...)`
   - If a row is missing (the invalid item), throw `UserAbortException`. The worker rolls back
     and records the order as **successful** (an expected rollback, counted in tpmC).
7. Update stock, once per supplying warehouse:
   - `useStoredProcedures=true` (default): `CALL updatestockN(wid, i1,q1,y1,r1, ..., iN,qN,yN,rN)`
   - otherwise: a JDBC batch of `UPDATE stock SET ... WHERE s_i_id=? AND s_w_id=?`
     (see the known issue in [CODE_REVIEW_GUIDE.md](CODE_REVIEW_GUIDE.md))

   New quantity: `s_quantity - qty` if that leaves at least 10, else `s_quantity - qty + 91`.
   The client computes `s_ytd` and `s_remote_cnt` from the values it read.
8. `INSERT INTO order_line (...) VALUES (...), (...), ...`: all 5–15 lines in **one** multi-row
   statement (one SQL text variant per line count, 5..15).

So the per-item loop of the spec becomes a constant number of round trips, whatever the order size.

**Retries:** NewOrder is the only transaction that is retried, up to `maxRetriesPerTransaction`
extra attempts (§6.6).

### 6.2 Payment (43%): record a customer payment

**Inputs:** random district. 85% of the time the customer belongs to the home warehouse and
district. 15% of the time it is a **remote** customer: random district of a different warehouse.
The customer is chosen **60% by last name** (`NURand(255)` syllable name) and **40% by id**. The
amount is 1.00–5000.00.

**SQL:**

1. Customer lookup:
   - by id: `SELECT c_first, ..., c_since FROM customer WHERE c_w_id=? AND c_d_id=? AND c_id=?`
   - by name: `SELECT ... FROM customer WHERE c_w_id=? AND c_d_id=? AND c_last=? ORDER BY c_first`,
     then take the row at position ⌈n/2⌉ (spec 2.5.2.2)
2. `UPDATE warehouse SET w_ytd = w_ytd + ? WHERE w_id=? RETURNING w_street_1, ..., w_name`
3. `UPDATE district SET d_ytd = d_ytd + ? WHERE d_w_id=? AND d_id=? RETURNING d_street_1, ..., d_name`
4. Bad-credit (`"BC"`) customer: `SELECT c_data ...`, then
   `UPDATE customer SET c_balance=?, c_ytd_payment=?, c_payment_cnt=?, c_data=? WHERE ...`
   (the payment details are prepended to `c_data`, which is truncated to 500 chars).
   Good-credit customer: `UPDATE customer SET c_balance=?, c_ytd_payment=?, c_payment_cnt=? WHERE ...`
5. `INSERT INTO history (...) VALUES (...)`
6. `COMMIT`

`WAREHOUSE.w_ytd` is updated by every Payment on that warehouse, and `DISTRICT.d_ytd` by every
Payment on that district. Together with NewOrder's `d_next_o_id`, these are the hot rows that cause
transaction conflicts at high per-warehouse concurrency.

### 6.3 OrderStatus (4%): query a customer's last order (read-only)

1. Customer lookup, 60% by name / 40% by id. Always the home warehouse; random district.
2. `SELECT o_id, o_carrier_id, o_entry_d FROM oorder WHERE o_w_id=? AND o_d_id=? AND o_c_id=? ORDER BY o_id DESC LIMIT 1`
   (served by `idx_order`)
3. `SELECT ol_i_id, ol_supply_w_id, ol_quantity, ol_amount, ol_delivery_d FROM order_line WHERE ol_o_id=? AND ol_d_id=? AND ol_w_id=?`
4. `COMMIT`

### 6.4 Delivery (4%): deliver the oldest undelivered orders

With a random carrier id 1–10, for each district `d` from 1 up to the terminal's district (see §9):

1. `SELECT no_o_id FROM new_order WHERE no_d_id=? AND no_w_id=? ORDER BY no_o_id ASC LIMIT 1`
   (skip the district if it is empty)
2. `DELETE FROM new_order WHERE no_o_id=? AND no_d_id=? AND no_w_id=?`. If this does not delete
   exactly 1 row, the transaction fails: another Delivery got there first.
3. `UPDATE oorder SET o_carrier_id=? WHERE o_id=? AND o_d_id=? AND o_w_id=? RETURNING o_c_id`
4. `UPDATE order_line SET ol_delivery_d=? WHERE ol_o_id=? AND ol_d_id=? AND ol_w_id=?`
5. `SELECT SUM(ol_amount) AS ol_total FROM order_line WHERE ...`
6. `UPDATE customer SET c_balance = c_balance + ?, c_delivery_cnt = c_delivery_cnt + 1 WHERE ...`
7. **`COMMIT` after each district.** Each district is its own database transaction (PR #106).
   This shortens the transaction and reduces conflicts.

Delivery runs synchronously inside the terminal. The spec allows it to be queued and run in
deferred mode.

### 6.5 StockLevel (4%): count low-stock items (read-only)

Runs with **`autoCommit=true`**, so each statement gets its own snapshot (allowed by spec 2.8.2.3).
It uses the terminal's fixed district and a random threshold 10–20.

1. `SELECT d_next_o_id FROM district WHERE d_w_id=? AND d_id=?`
2. `{ ? = call getstockcounts(?, ?, ?, ?) }` with `(w_id, d_id, d_next_o_id - 20, d_next_o_id, threshold)`.
   The function body:
   ```sql
   SELECT ARRAY(SELECT DISTINCT(ol_i_id) FROM order_line
                WHERE ol_w_id=$1 AND ol_d_id=$2 AND ol_o_id >= $3 AND ol_o_id < $4) INTO item_ids;
   SELECT COUNT(s_i_id) INTO result FROM stock
    WHERE s_w_id=$1 AND s_i_id = ANY(item_ids) AND s_quantity < $5;
   ```

### 6.6 Retries, rollbacks and failures

The retry logic lives in `Worker.doWork()`:

- Each piece of work borrows **one** pooled connection, which is reused across its retry attempts.
  On YugabyteDB it runs `SET yb_enable_expression_pushdown to on` first. Autocommit is disabled
  for everything except StockLevel.
- **Expected rollback:** `UserAbortException` from NewOrder means rollback, status
  `USER_ABORTED`, recorded as a success.
- **`SQLException`** (serialization failure `40001`, `53200` out of memory, `XX000` internal
  error, or anything else with a SQLState) means rollback (errors ignored, e.g. when the node is
  down), status `RETRY`. An `SQLException` with a *null* SQLState leaves the status `UNKNOWN`: it
  is recorded as a failure and not retried.
- **Any other `Exception`/`Error`** means status `RETRY` *without* a rollback (K20).
- **Only NewOrder retries**, up to `1 + maxRetriesPerTransaction` attempts in total. The other
  four transactions stop after the first failed attempt.
- Failed attempts are counted per transaction type and attempt number. They are shown in the
  "RETRY ATTEMPTS" and "FAILURE LATENCIES" tables when `--vv` is given.

## 7. Random input generation (NURand)

TPC-C skews access with the non-uniform random function (clause 2.1.6):

```
NURand(A, x, y) = (((random(0, A) | random(x, y)) + C) % (y - x + 1)) + x
```

| Use | A | Range | C (`TPCCUtil`) |
|-----|---|-------|---|
| Customer id | 1023 | 1–3000 | `C_ID_C = 259` |
| Item id | 8191 | 1–100000 | `OL_I_ID_C = 7911` |
| Customer last name (load) | 255 | 0–999 | `C_LAST_LOAD_C = 157` |
| Customer last name (run) | 255 | 0–999 | `C_LAST_RUN_C = 223` |

The spec requires `|C_LAST_RUN - C_LAST_LOAD|` to be in [65, 119]. Here it is 66. The constants are
hard-coded rather than drawn at random per run.

Last names are built from three syllables of
`{BAR, OUGHT, ABLE, PRI, PRES, ESE, ANTI, CALLY, ATION, EING}` indexed by the digits of a
0–999 number (e.g. 371 is `PRICALLYOUGHT`).

## 8. The headline metric: tpmC and efficiency

```
tpmC       = (NewOrder transactions completed in the measurement window) * 60 / runtime_seconds
efficiency = tpmC / (12.86 * warehouses) * 100%
```

- NewOrders that hit the expected 1% rollback **count** (PR #107).
- A NewOrder counts if the state is MEASURE at the end of its terminal cycle (after the think-time
  sleep), and was WARMUP or MEASURE when the work was fetched (PR #110). See
  [METRICS_AND_RESULTS.md](METRICS_AND_RESULTS.md#what-gets-recorded) for the edge effects.
- **12.86** is the theoretical maximum tpmC per warehouse with spec keying and think times. The
  mix-weighted mean cycle (keying + think) is about 20.99 s, so 10 terminals × 60/20.99 × 45%
  is about 12.86 NewOrders per minute. An efficiency near **100%** means the database keeps up
  with the offered load. Lower values mean transactions are taking too long, failing, or the
  client is the bottleneck.
- In a multi-client run, each client reports tpmC and efficiency **for its own slice** of
  warehouses (`--warehouses`). Sum tpmC across clients, or use `--merge-json-results`.

See [METRICS_AND_RESULTS.md](METRICS_AND_RESULTS.md) for every number the tool prints.

## 9. Deviations from the specification

This tool is a load generator for database performance work, not a TPC-certified kit. Known
differences:

| Area | Spec | This implementation |
|------|------|--------------------|
| Delivery scope | All 10 districts per Delivery | Districts `1..d`, where `d` is the terminal's own district (5.5 on average). A side effect of 10 terminals per warehouse with one district each. |
| Delivery execution | May be deferred/queued | Synchronous, and **one DB transaction per district** |
| Retries | — | Only NewOrder is retried |
| NewOrder item processing | Per-item loop (pseudo-code) | Set-based `IN (...)` reads, procedure-based stock update, multi-row insert (allowed: "submissions may use what is optimal") |
| Payment ordering | Warehouse, district, then customer | Customer read first, then warehouse/district updates |
| StockLevel | Join of `ORDER_LINE` and `STOCK` | Server-side function `getstockcounts` |
| NURand C constants | Chosen randomly per run | Hard-coded |
| Random string lengths | e.g. `i_data` 26–50, `s_dist_xx` 24, `c_data` 300–500 | `TPCCUtil.randomStr(n)` returns **n−1** characters, so every generated alpha string is one character short (`i_data`/`s_data` 22–49, `s_dist_xx`/`ol_dist_info` 23, `c_data` 299–499, ...). |
| Consistency checks, ACID tests, pricing, durability tests | Required for a TPC result | Not implemented |
| Measurement interval | ≥ 2 h steady state, with ramp-up rules | Configurable: `<runtime>` (sample: 1800 s) after `--warmup-time-secs` |
| Isolation | Serializable-equivalent for most transactions | Configurable; the sample config uses `REPEATABLE READ` |
